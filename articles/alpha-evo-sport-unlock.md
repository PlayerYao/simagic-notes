# SIMAGIC Alpha EVO Sport 型号解锁

Alpha EVO Sport 与 Alpha EVO 共用固件。设备通过 Flash 中的型号标记选择预设，解锁的核心是修改这个标记，再由原固件应用 EVO 对应的参数。

在测试设备上，SimPro 显示从 Sport／9 N·m 变为 EVO／12 N·m，断电重启和升级至 2.3.6 后均保持。实际轴端扭矩未测量。

## 固件比较

SFU 升级包由 64 字节包头和 AES-256-CTR 加密载荷组成。沿 SimPro 的升级包解析代码还原解码流程后，可以取得 ARM Thumb 固件进行静态分析。

现有 11 个样本的比较结果：

| 版本 | 样本数量 | 同版不同型号的载荷 |
| --- | ---: | --- |
| 2.2.3 | 2 | 相同 |
| 2.2.8 | 3 | 相同 |
| 2.3.4 | 3 | 相同 |
| 2.3.5 | 3 | 相同 |

Sport 与 EVO 使用同一个分发包；现有 Pro、Ultra 的同版样本也共享载荷。程序包含多套型号预设，由设备配置决定使用哪一套。

## 型号配置

Flash 配置分为四个槽，总长度 564 字节：

| 槽 | 长度 | 内容 |
| --- | ---: | --- |
| 0 | 8 字节 | 设备序列信息 |
| 1 | 8 字节 | 用途未完全确定 |
| 2 | 528 字节 | 参数表 |
| 3 | 20 字节 | 末尾 4 字节保存型号标记 |

启动时，固件读取型号标记，结合设备类别选择预设。预设中的档位参数随后用于生成设备信息报告和 USB 产品名称，SimPro 根据报告显示型号。

```text
Flash 型号标记 → 预设选择 → 运行参数
                              ├─ 设备信息报告 → SimPro 型号显示
                              └─ USB 产品名称
```

型号标记是预设选择值。扭矩等参数仍由固件中的对应预设提供。

## 型号写入命令

固件保留了一条修改型号的命令。请求经 HID 报告解析、入队、解密和校验后，进入型号处理器。

处理器检查两个条件：

- 请求的目标型号是否有对应分支。
- 当前设备类别是否允许进入该分支。

满足条件后，保存目标型号标记，并立即调用预设应用函数。逻辑可简化为：

```text
目标型号匹配，且设备类别匹配
    → 写入该分支规定的型号标记
    → 保存配置
    → 应用对应预设
```

**写入的是程序中的预设常量，请求值只用于选择分支。** 因此，这条命令支持有限的型号切换，不能任意设置输出扭矩。

已分析的分支没有恢复原厂 Sport 标记的操作，目前也没有经过验证的回退流程。

## 加密与会话状态

设备命令使用独立于 SFU 升级包的加密通道。构造请求需要匹配设备当前的派生结果和校验前缀。

主要处理过程：

```text
设备相关信息 + 伪随机状态
          ↓
       密钥派生
          ↓
设备信息与派生结果 → 摘要前缀
          ↓
       加密载荷
```

其中有几处实现细节需要按固件还原：

- 伪随机数经过特定归约，不能直接取低字节。
- 前缀使用 MD5 变体，不能直接替换成标准 MD5。
- 输入字段的顺序、宽度和字节序必须一致。

初始化时，固件设置伪随机状态并执行派生；另一条查询路径也会执行派生，但沿当前状态继续计算。因此，同一台设备的派生结果也会变化。

**请求与设备状态必须匹配。** 当前实验请求使用了设备专属数据，不能直接用于另一台基座。

### HID 长度

设备查询返回的最大 Feature Report 缓冲区长度为 241 字节，目标报告的有效长度为 64 字节。对 Windows HID 标准驱动路径的分析表明，实际传输使用对应报告的长度。

构造主机缓冲区时，需要区分 API 所需容量与 USB 实际传输长度。

## 实测结果

| 阶段 | 结果 |
| --- | --- |
| 第一次发送 | 接口返回成功，型号回读仍为 9 |
| 断电重启 | 型号仍为 9 |
| 调整启动和会话条件后再次发送 | 同一请求使型号回读变为 12 |
| 再次断电重启 | 型号保持 12，USB 产品名称为 Alpha EVO |
| 用户升级至 2.3.6 后回读 | 型号仍为 12 |

首次失败的排查结论是：**SimPro 先前与基座通信，推进了密钥派生状态，使按上电初始状态计算的密钥和校验前缀失效。** 发送时虽然已经关闭 SimPro，但设备内部状态并不会随主机程序退出而复位。

随后重新断电上电，保持 SimPro 关闭，并避开会触发重新派生的查询，使用完全相同的请求再次发送，型号成功变为 12。同一请求在恢复初始状态后生效，支持上述密钥状态变化的判断。

发送接口返回成功，只说明主机调用完成。是否生效需要设备回读；是否持久保存需要断电后再读。

## 配置保存与升级保留

配置更新采用以下流程：

```text
复制现有配置 → 修改目标槽 → 擦除相关区域 → 回写配置
```

重新上电后，启动代码读回型号标记并应用预设，因此型号变化可以跨重启保留。

应用程序与持久配置位于不同区域。普通升级可以替换程序并保留配置，新固件继续读取已有标记。测试设备升级至 2.3.6 后保持目标型号，与这一机制相符。

配置更新涉及擦除和回写，掉电或异常中断可能影响其他槽；本次没有完整配置区的前后比对，也没有验证异常恢复。

## 版本范围

四个静态分析版本中，均能找到对应的型号读写、预设选择和派生逻辑，部分代码位置及 RAM 地址随版本变化。尚未发现能证明该机制仅存在于 2.2.3 的专属条件。

| 版本 | 验证程度 |
| --- | --- |
| 2.2.3 | 完成型号改写、回读与断电保持实验 |
| 2.2.8／2.3.4／2.3.5 | 已分析相关代码，未完成改写实验 |
| 2.3.6 | 已有改写后升级保持记录，未验证首次改写 |

## 分析工具与 AI 模型

分析在 WSL 中进行，设备查询与实验通过 Windows PowerShell 调用系统 HID 接口。

### 工具与技术

| 工具／技术 | 用途 |
| --- | --- |
| 7-Zip | 从官方安装包中提取 SimPro、DLL 和 SFU 固件。 |
| Python、SHA-256、二进制比较 | 解析包头、比较载荷、提取结构，并核对不同版本的对应代码。 |
| Python `cryptography` | 还原 SFU 的 AES-256-CTR 解码流程。 |
| LLVM 17、ARM Thumb 反汇编 | 通过 Python `ctypes` 调用 LLVM，追踪配置读写、型号分派及加密处理。 |
| `objdump`、PE 解析、字符串与交叉引用检索 | 分析 SimPro 和 Windows HID／USB 驱动，定位报告解析、函数调用和传输长度。 |
| REA | 辅助打开目标二进制、检查 PE 资源。 |
| PowerShell 5.1、Windows HID API | 查询设备能力、发送请求、读取型号并验证重启后的状态。 |

固件分析主要沿“参数从哪里读取、在哪里被修改、修改后由谁使用”追踪，同时对照其他版本的相应函数。协议部分分别核对字节序、派生算法、摘要计算与报告长度。

### 模型分工

原始研究使用 **Pi 与 pi-subagents** 组织主会话和并行任务。会话记录中实际使用的模型如下：

| 模型 | 主要工作 |
| --- | --- |
| **GPT-6.1 Sol**（`gpt-6.1-sol`） | 主会话前期分析与研究路线梳理。 |
| **DeepSeek V4.1 Flash**（`deepseek-v4.1-flash`） | 主会话推进、并行探索、辅助脚本编写，以及早期技术博客起草。 |
| **GPT-6 Astra**（`gpt-6-astra`） | 关键代码路径分析、独立证据复核、执行方案审查，以及后续技术稿撰写。 |

前期由 DeepSeek 并行探索多个假设，后期将关键分析与审查交给 Astra。复核中修正了前缀恒零、读写命令分类、报告字段位置和传输长度等判断，最终以反汇编、原始字节和设备回读结果核对。
